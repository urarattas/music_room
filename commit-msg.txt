feat(server): 添加日志系统，并修复 WebSocket 关闭事件不触发导致的内存泄漏

日志系统
- 新增 server/logger.js
  - 分级 debug/info/warn/error，各级别可独立开关
  - 按天分文件 logs/server-YYYY-MM-DD.log
  - 超过 LOG_MAX_SIZE 自动轮转为 .1 .2 ...，最多保留 LOG_MAX_FILES 份
  - 超过 LOG_MAX_DAYS 的旧文件自动删除（主日志按文件名日期判断，
    轮转文件按修改时间判断）
  - 写文件失败时自动降级为仅控制台，不影响服务运行
  - logger.stats() 返回日志概况，/api/health 里已暴露
- 记录内容：WebSocket 连接建立/断开、成员加入/离开/切换房间、
  播放曲目、聊天消息、HTTP 请求、消息解析失败、无效曲目、连接错误、
  HTTP 处理失败、未捕获异常、未处理的 Promise 拒绝
- 日志包含毫秒时间戳、级别、结构化附加信息（连接 ID、客户端 IP、
  房间、昵称等）
- 客户端 IP 优先取 X-Forwarded-For，其次 X-Real-IP，
  兼容反向代理部署
- 配置项全部走环境变量：LOG_LEVEL / LOG_DIR / LOG_MAX_SIZE /
  LOG_MAX_FILES / LOG_MAX_DAYS / LOG_CONSOLE
- Docker：镜像内预建 /app/logs 并 chown 给 node 用户，
  compose 挂载卷持久化日志

修复内存泄漏（写日志时发现）
server/ws.js 的 close() 与收到关闭帧的处理里，都先把 readyState
置为 3(CLOSED) 再调用 _onClose()，而 _onClose() 开头有
if (this.readyState === 3) return 的守卫 —— 于是 close 事件
永远不触发。

后果：客户端正常关闭时，服务端的 close 处理器不会执行，
房间成员列表里会一直残留该用户，连接与房间都无法回收。
长期运行就是内存泄漏。

修复：把中间状态改为 2(CLOSING)，让 _onClose() 能正常触发。
现在 close 事件正常触发，房间成员与空房间都会被正确清理。
